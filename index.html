AI Agent · 一份看得懂的整体梳理

它不是更会聊天的模型，
是能把活干完的软件。

这份报告只讲一件事：AI Agent 是什么、怎么变成今天这样、内部怎么运转、现在真能做什么、能用在哪些地方。全是概念和事实，不谈融资和市场。

五个板块约 8 分钟零表格结尾附术语速查
从右边这段动画开始：一次任务是怎么跑完的
序 · 01 目标

先给一个目标，不是一串指令。

把一份 40 页的资料变成一页能决策的摘要，5 分钟内交。目标是可验收的结果，不是操作步骤。

目标里必须写清"什么算完成"，否则它只能猜。
序 · 02 拆解

它自己拆步骤。

定位数据源 → 抽取事实 → 交叉验证 → 生成摘要 → 自检格式。每一步都是能检查的动作。

能被检查的步骤，才谈得上重试和审计。
序 · 03 工具

该查的去查，该算的去算。

检索、跑代码、查数据库、读网页。模型只决定用哪个工具，真正动手的是工具本身。

让它没机会编，比提醒它别编有效得多。
序 · 04 观察

读完结果再往下走。

工具返回的真实结果先回到它手里，而不是继续凭记忆推理。

忽略结果硬往前走，是长任务崩掉最常见的原因。
序 · 05 自检

不合格就重做一遍。

三道闸门：来源可追溯、数字一致、格式合规。只有绿灯才放行。

十步各 95% 正确，串起来只剩约 60%，所以闸门必须自动。
序 · 06 交付

交出能被验收的结果。

成果盖戳交付，高风险动作由人确认，这次的有效路径回写进记忆。

可验收、可回滚、可审计——缺一个就不敢真用。
板块一 · 概念

先分清它是什么，再谈它多能干

行业里"Agent"这个词被用得很松。这里给一个可操作的判断标准，再按四层把相关概念一次摆清——包括 skills 这类工程概念。

一 · 三个必要条件

目标、工具、循环，缺一不可。

没有目标只是聊天；没有工具只能空谈；没有循环，一次失败就结束。三个凑齐，它才可能在没人逐步指示的情况下把活干完。

判断标准就一句话：它能不能自己决定下一步，并产生真实动作。
一 · 分界线

聊天改变你的想法，
Agent 改变系统状态。

它会读文件、发请求、改数据、开单子。错了是有代价的——所以权限、审计、回滚是它的标配，不是加分项。

这就是为什么同样叫"AI 应用"，风险等级完全不是一回事。
一 · 四层地图

概念别硬背，按四层放。

构成层：模型、上下文、工具、记忆、规划、循环、状态、沙箱、人在环。组织层：工作流与自主、单与多智能体、子智能体。工程层：skills、MCP、约定文件、hooks、检索、评测、可观测。安全层：提示注入、最小权限、身份、审计、接地。

最容易混的一对：工具是"能做什么"，skill 是"这件事该怎么做"。

自主性阶梯：从问答到自己干活

点任意一级，看它的判断标准、人扮演什么角色、失败代价有多大。

六组最容易混的概念

工具 vs 技能

工具是"能做什么"（检索、跑代码）；skill 是"这件事该怎么做"（说明书＋脚本＋模板）。

提示词 vs 上下文

提示词是你说的话；上下文是它此刻能看到的全部信息，包括工具返回和检索结果。

记忆 vs 检索

记忆是它记住的；检索是它现查的。前者要决定写什么、何时忘，后者要决定查哪里、信不信。

工作流 vs Agent

工作流的路径写死，稳定便宜；Agent 自己决定路径，灵活但更难查。生产系统多数是两者混合。

单智能体 vs 多智能体

一个干完简单可控；分工协作能并行、能隔离权限，但通信损耗和成本都翻倍。

微调 vs 检索 vs 长上下文

改它的脑子（微调）／给它资料（检索）／全都塞进去（长上下文）。多数情况先试后者。

板块二 · 历史

它不是突然出现的，三条线凑齐才成立

模型会推理、接口能动手、系统能被管住——这三件事在过去十年里分别成熟，才有了今天的 Agent。

二 · 三条线

模型、接口、治理，各成熟一次。

模型从"续写文本"变成"遵循指令并多步推理"；接口从"只能说话"变成"能调用工具、能操作界面"；治理从"能用就行"变成"权限、审计、可回滚"。

三者缺一，Agent 就只能停在演示视频里。
二 · 2022–2023

从"会说"到"会做"。

"推理—行动—观察"的循环被系统化提出；对话产品让大众第一次用上大模型；工具调用让模型第一次能驱动外部系统。同期一批全自动实验翻车，证明没有评测就无法复现。

这一阶段最大的收获不是能力，而是知道了缺什么。
二 · 2024–2026

从"能演示"到"能交付"。

多模态和长上下文打开输入；计算机操作让没有接口的老系统也能被操作；编码 Agent 成为第一个规模化跑通的场景；工具协议统一之后，生态开始复用；企业侧开始把评测、可观测、权限列为硬性要求。

主题词从"能力展示"换成了成功率、成本、回滚与审计。

八个节点

点年份看那一年解决了什么、又留下了什么。

三条反复出现的教训

一、演示容易，复现难。同一个任务跑两次结果不同，是早期 Agent 的通病。可复现性是把演示变成产品的第一道坎。

二、有没有自动裁判，决定进展快慢。编码跑得最快，是因为编译器与测试会立刻告诉你对错。没有裁判的领域，进展慢一个数量级。

三、能力涨了，权限必须跟上。能读网页就可能被注入，能操作终端就可能删错东西。每一次能力跃升都会把安全问题推到台前。

板块三 · 原理

它是怎么跑起来的

把结构拆开看，好处很实际：效果不好时你能定位到是哪一层的问题，而不是笼统地说"模型不行"。

三 · 执行循环

七步走完一轮，每步都有坑。

接收目标 → 拆解计划 → 选择工具 → 执行动作 → 观察结果 → 校验并决定是否重试 → 交付与留痕。每一步都有最常见的失败方式，工程上防的就是这些点。

步骤可检查，才可重试；可重试，长任务才跑得完。
三 · 六层构成

六层积木，各管一段。

模型层决定上限；上下文层决定它此刻看到什么；记忆与状态层决定连续性；工具与协议层决定它能做多少事；编排层决定长任务能不能跑完；评测与治理层决定它能不能上生产。

多数"效果不好"其实不在模型层，而在上下文和编排。
三 · 一个还是多个

多智能体不是默认答案。

只有任务能独立分解、需要不同权限、或需要独立审核者时，分工才划算。否则通信损耗、状态不一致、成本翻倍，失败原因还更难定位。

十步各 95% 正确，串起来只剩约 60%——所以先用单体跑通并建立评测，再考虑拆分。

一轮任务的分步演示

点任意步骤，或让它自己播一轮。重点不是流程，是每步最容易出错的地方。

板块四 · 现状

现在真能做什么，还做不好什么

这一节尽量把边界说清楚。对 Agent 失望的人，多半不是技术不行，而是预期被演示视频拉得太高。

四 · 已经跑通

短任务已经真的可用。

理解模糊指令、写代码、总结、翻译、抽取结构化信息；工具调用稳定到能上生产；3 到 10 步、且有明确验证信号的短任务；带出处的检索问答；截图、表格、扫描件的理解。

共同点：有明确的对错，或者错了也不致命。
四 · 六个瓶颈

卡住的地方，大多不是聪明程度。

错误累积、缺少裁判、上下文与状态膨胀、权限与安全、成本与延迟、组织与流程没适配。前三个是技术问题，后三个往往是组织问题。

技术问题可以迭代；组织问题会一直卡着不动。
四 · 上线判断

能不能做，看三条。

结果能不能被验证、错了能不能回滚、需要的数据能不能合法拿到。三条都过，才谈得上真做；缺一条，先做辅助版本，人确认后再执行。

这也是为什么编程领域跑得最快——它三条全占。

已经基本解决

  • 单步能力：理解模糊指令、写代码、总结、翻译、结构化抽取
  • 工具调用：函数调用的稳定性已可用于生产
  • 短任务闭环：3–10 步、有验证信号的任务
  • 检索与引用：能基于资料回答并给出来源
  • 多模态输入：截图、表格、扫描件达到可用水平
  • 成本：同能力推理的单位价格明显下降

仍然困难

  • 长任务：步骤一多，错误累积，几十步后成功率下滑
  • 无裁判的场景：没有自动验证手段，"好不好"无法量化
  • 跨系统状态：多个系统之间的一致性极难保证
  • 安全边界：提示注入、越权、凭据管理尚无成熟范式
  • 评测标准：缺少公认的任务级基准，供应商数据不可比
  • 组织适配：流程没数字化、责任没定义、人不知道怎么配合

01错误累积

十步各 95% 正确，串起来约 60%。这就是"演示很好、批量很糟"的数学原因。

02缺少裁判

代码有测试、客服有解决率，但"这份分析好不好"没有自动答案。没有裁判就无法稳定优化。

03上下文与状态

任务跑长之后，关键信息被淹没、早前的决定被遗忘。这是信息管理问题，不是窗口不够大。

04权限与安全

要干活就得有权限，有权限就意味着一次错误可能不可逆。权限设计比模型选型更决定成败。

05成本与延迟

一个任务可能包含几十次调用与重试。延迟还直接影响体验：没人愿意等三分钟看进度条。

06组织与流程

谁审批、出错谁负责、绩效怎么算、流程要不要改——这些决定了项目什么时候能上线。

板块五 · 应用

能用在哪些地方，从哪儿开始

同一项技术，在不同场景的落地速度差好几年。差别不在任务难不难，而在三件事：能不能自动验证、错了能不能低成本回滚、数据能不能合法拿到。

五 · 九个场景

有的已经替代工时，有的还在演示。

编程跑得最快，因为它自带编译与测试作为裁判；客服与销售次之，因为指标清晰、流程标准；深度研究、文档、数据分析处在中间；浏览器操作、通用助手、流程自动化各有卡点；垂类行业最慢，因为要承担专业与法律责任。

规律：能自动判对错的先跑通，需要人当裁判的慢一拍，要担责的最慢。
五 · 上手路径

先当助手用，再当流程用。

第一步是把它当成能跑腿的初级同事：写清目标、给足上下文、定好验收标准，自己盯结果。第二步才是把稳定的部分固化成流程，让它在无人值守时也能跑。

反过来做（一上来就全自动）通常会在权限和异常处理上卡死。
五 · 盯什么

接下来只看一件事。

不是看模型分数又涨了多少，而是看"长任务的一次成功率"有没有出现台阶式提升。它决定了 Agent 能不能从辅助工具变成真正交付成果的系统。

判断信号：评测与可靠性是否变成像 CI/CD 一样的基础设施。

九个场景与成熟度

编程与软件工程

直接改代码：读仓库、写补丁、跑测试、开 PR。目前唯一被大规模证明能替代真实工时的形态。

为什么跑通：自带验证信号与回滚机制。

客户服务与销售

不只是回答，而是查订单、改地址、发补偿、建工单、推进销售阶段。

卡点：错误答复的合规风险；写操作需要额度与审批。

深度研究与情报

给一个开放问题，自动做几十轮检索、阅读、交叉验证，输出带出处的报告。

卡点：来源质量参差；可能被网页内容误导。

办公与法务文档

合同审阅、条款比对、会议纪要到行动项、报表与初稿。

卡点：专业责任边界；长文档的一致性。

数据分析与商业智能

从自然语言问题到取数、清洗、出图、写结论，并解释口径。

卡点：口径与权限复杂；"看起来对"的图最危险。

浏览器与计算机操作

像人一样看屏幕、点按钮、填表单，适合没有 API 的老系统。

卡点：慢、脆（界面一改就失效）、错误不可逆。

通用个人/团队助手

邮箱、日历、待办、文档打通，能安排、汇总、起草、跟进。

卡点：跨应用权限整合极难；价值难量化。

流程自动化（RPA 升级）

把规则型自动化升级成能处理例外的自动化：异常单据、非标邮件。

卡点：与既有系统耦合深；异常处理的责任归属。

垂类行业

金融合规核查、病历与文献整理、案例检索、个性化辅导。

卡点：监管、责任、数据合规，普遍要求强人在环。
